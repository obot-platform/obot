# Agent identities: validation matrix and manual QA

Validation of the [agent identities ADR](../../adr/2026-11-17-agent-identities.md) against the ODP's test plan. Each
row says which automated tests cover it, and what is left for manual QA in the Testing column. Unit tests run with
`make test` (set `OBOT_TEST_POSTGRES_DSN` for the Postgres variants, as CI does). The integration tests in
[`agent_identities_test.go`](agent_identities_test.go) run with `make test-integration` against one in-process server
with authentication off, SQLite and Docker. `TestAgentVMCPConnection_NPXEverything`, like `TestMCPServerLifecycle_NPXEverything`, also needs MCP containers that can reach the npm registry. The e2e tests in
[`tests/e2e/llmgateway/agents_test.go`](../e2e/llmgateway/agents_test.go) run with `make test-e2e-llm-gateway` against two
real replicas on Postgres with authentication on.

## Manual QA checklist

Use a test deployment with two replicas on Postgres, authentication on, and a real OAuth provider (for example a
GitHub OAuth app). Use made-up agent names, and never paste real keys into the issue.

- [ ] **Q1. Same numeric ID.** Create agents until one has the ID of an existing user (for example 3). Give both access to the same shared vMCP and a model with a per-user budget. Connect both. Check that **Identity & Access > Agents > (agent)** and the user see separate connections, that budget usage and audit logs list them separately (the agent with an **Agent** badge), and that each one's key works only as itself.
- [ ] **Q8. Agent OAuth on the vMCP.** Name one agent in two profiles of a vMCP that grant different components: the agent gets the tools of both, and **Agent setup** on the vMCP's page lists the components of both. Remove the agent from one profile: it keeps only the other profile's tools. Authorize an OAuth component under **Agent setup**: a second agent that a profile grants the component uses the same grant without another authorization, and an agent whose profiles don't grant the component can't reach it. **Revoke** it: both agents' readiness shows `oauth_required`, and their connections get `409 agent_oauth_required`. Authorize it again, then remove the component from the vMCP: the grant is gone. Delete the vMCP: its grants are gone. Rename and delete profiles: no grant changes. The profile editor shows no agent setup.
- [ ] **Q9. Existing `*` policies.** Upgrade a deployment that has a vMCP profile, a model access policy and a skill access rule for **All Obot Users**, and an MCP guardrail filter for everyone. Users keep their access, and the filter still checks their calls. Create an agent with a key for MCP, LLM and Skills: its vMCP connection gets 403, its model requests get 403, its skill list is empty, and its page lists no access and both problems. Name the agent in each policy: each then grants it access. The guardrail filter checks the agent's calls only once it names the agent.
- [ ] **Q10. Rollback.** Follow the rollback steps in the docs (**Agent identities > Roll back agent identities**), downgrade to the previous release, and check that it starts, users sign in, user API keys work, and the admin API key list loads. Upgrade again and check that agents' audit history is still there.
- [ ] **Q11. UI.** `?view=agents` and `/identity-access/agents/...` redirect to **API Keys**. The **Agents** tab appears with authentication on and off. On a catalog-synced vMCP, only the vMCP's **Agent setup** is editable. The model, skill, vMCP profile and guardrail filter editors offer **All Obot Users** and specific agents, and no **All Agents** or **All Users** option. **Agent setup** appears on the vMCP's page only when a saved profile names an agent, lists only the components those profiles grant, and has no configuration fields. Profiles have no agent setup. No configuration value or configured URL is ever shown.
- [ ] **Q12. Catalog-synced agents.** In a Git catalog, name an existing agent by ID in a vMCP profile, and a made-up agent ID in another vMCP's profile. `obot mcp validate-catalog` passes. After sync, the first vMCP grants the agent (authorize its OAuth components under the vMCP's **Agent setup** and connect with its key), and the second syncs and grants nobody. Name the agent in two profiles of one vMCP: validation and sync pass, and the agent gets both profiles' tools. Resync: the vMCP's grants remain. `agent` with `*` is refused with an error that says agents must be named by ID.
- [ ] **Q13. Configuration agents can't get.** Give an agent a vMCP whose component has a required **User Allowed** value, or a hostname-constrained remote whose **Server URL** isn't fixed. Its connection gets `409 agent_configuration_required` naming the component and key, its readiness says `configuration_required`, and the vMCP's **Agent setup** shows the component's configuration as not ready, telling you to fix the value on the vMCP or catalog entry or stop granting the component. Set the value as **Fixed** on the vMCP: the agent connects. Make the value optional instead: the agent connects without it. Stop granting the component in the agent's profiles: the agent connects to the rest.
