# Agent identities: validation matrix and manual QA

Validation of the [agent identities ADR](../../adr/2026-11-17-agent-identities.md) against the ODP's test plan. Each
row says which automated tests cover it, and what is left for manual QA in the Testing column. Unit tests run with
`make test` (set `OBOT_TEST_POSTGRES_DSN` for the Postgres variants, as CI does). The integration tests in
[`agent_identities_test.go`](agent_identities_test.go) run with `make test-integration` against one in-process server
with authentication off, SQLite and Docker. `TestAgentVMCPConnection_NPXEverything`, like `TestMCPServerLifecycle_NPXEverything`, also needs MCP containers that can reach the npm registry. The e2e tests in
[`tests/e2e/llmgateway/agents_test.go`](../e2e/llmgateway/agents_test.go) run with `make test-e2e-llm-gateway` against two
real replicas on Postgres with authentication on.

## Manual QA checklist

Use a test deployment with two replicas on Postgres, authentication on, and a real OAuth provider (for example a
GitHub OAuth app). Use made-up agent names, and never paste real keys into the issue.

- [ ] **Q1. Same numeric ID.** Create agents until one has the ID of an existing user (for example 3). Give both access to the same shared vMCP and a model with a per-user budget. Connect both. Check that **Identity & Access > Agents > (agent)** and the user see separate connections, that budget usage and audit logs list them separately (the agent with an **Agent** badge), and that each one's key works only as itself.
- [ ] **Q8. Agents and preconfigured OAuth.** Name one agent in two profiles of a vMCP that grant different components: the agent gets the tools of both. Remove the agent from one profile: it keeps only the other profile's tools. Open an OAuth component's settings in the vMCP designer and **Authorize** it in its **OAuth** section: a second agent that a profile grants the component uses the same account without another authorization, and an agent whose profiles don't grant the component can't reach it. Authorize a remote component that no profile grants to an agent: it works. **Revoke** the first component: both agents' readiness shows `oauth_required`, and their connections get `409 agent_oauth_required`. Authorize it again, then remove the component from the vMCP: its preconfigured OAuth is gone. Delete the vMCP: all of its preconfigured OAuth is gone. Rename and delete profiles: nothing changes. On the agent's page, each **vMCP readiness** link opens the component's settings in the vMCP designer.
- [ ] **Q9. Existing `*` policies.** Upgrade a deployment that has a vMCP profile, a model access policy and a skill access rule for **All Obot Users**, and an MCP guardrail filter for everyone. Users keep their access, and the filter still checks their calls. Create an agent with a key for MCP, LLM and Skills: its vMCP connection gets 403, its model requests get 403, its skill list is empty, and its page lists no access and both problems. Name the agent in each policy: each then grants it access. The guardrail filter checks the agent's calls only once it names the agent.
- [ ] **Q10. Rollback.** Follow the rollback steps in the docs (**Agent identities > Roll back agent identities**), downgrade to the previous release, and check that it starts, users sign in, user API keys work, and the admin API key list loads. Upgrade again and check that agents' audit history is still there.
- [ ] **Q11. UI.** `?view=agents` and `/identity-access/agents/...` redirect to **API Keys**. The **Agents** tab appears with authentication on and off. On a catalog-synced vMCP, the definition is read-only, but each remote component's **OAuth** section can authorize and revoke. The model, skill, vMCP profile and guardrail filter editors offer **All Obot Users** and specific agents, and no **All Agents** or **All Users** option. The vMCP page has no **Agent setup** tab, and profiles have no agent setup. Each remote component's settings have an **OAuth** section with the state (not required, needs authorization, authorized with who and when, or invalid with the reason), **Authorize**, **Revoke** with a confirmation, and the warning that everyone using the vMCP acts upstream as the authorized account. An auditor sees the state, and no **Authorize** or **Revoke**. No configuration value or configured URL is ever shown.
- [ ] **Q12. Catalog-synced agents.** In a Git catalog, name an existing agent by ID in a vMCP profile, and a made-up agent ID in another vMCP's profile. `obot mcp validate-catalog` passes. After sync, the first vMCP grants the agent (authorize its OAuth components in their settings in the vMCP designer and connect with its key), and the second syncs and grants nobody. Name the agent in two profiles of one vMCP: validation and sync pass, and the agent gets both profiles' tools. Resync: the vMCP's preconfigured OAuth remains. `agent` with `*` is refused with an error that says agents must be named by ID.
- [ ] **Q13. Configuration agents can't get.** Give an agent a vMCP whose component has a required **User Allowed** value, or a hostname-constrained remote whose **Server URL** isn't fixed. Its connection gets `409 agent_configuration_required` naming the component and key, and its readiness on the agent's page says `configuration_required`, names the component and key, and links to the component's settings in the vMCP designer. Set the value as **Fixed** on the vMCP: the agent connects. Make the value optional instead: the agent connects without it. Stop granting the component in the agent's profiles: the agent connects to the rest.
- [ ] **Q14. Preconfigured OAuth for users.** Use a shared vMCP with two remote OAuth components, X and Y, whose provider shows which account a call uses (for example a tool that returns the signed-in user), and a profile that grants both to two users, A and B, and an agent. Before anything is preconfigured, A connects and authorizes X and Y with A's own accounts. Then, as an administrator, **Authorize** X in its settings with a shared account: the **OAuth** section shows the warning and who authorized it and when.
  - B connects from an MCP client: B is asked to authorize only Y, in the client's OAuth flow and on the setup page. B's and A's calls to X, and the agent's, all act as the shared account. A's calls to Y act as A, and B's as B. X isn't listed among A's authenticated components.
  - **Revoke** X: B is asked to authorize X on the next connection. A's calls to X act as A again, without a prompt. The agent's readiness shows `oauth_required`.
  - Authorize X again, then revoke the token at the provider, or change the **Server URL** that the vMCP fixes for X: the next call to X from A or B gets `409` with `preconfigured_oauth_invalid` naming X, and no OAuth prompt. The agent gets `409 agent_oauth_required` with `oauth_invalid`. The **OAuth** section shows X as invalid, with the reason. Authorize X again: users and the agent work again.
  - As an auditor, the **OAuth** section shows the state with no **Authorize** or **Revoke**, and `POST` and `DELETE` on `/api/vmcps/{vmcp_id}/components/{component_id}/preconfigured-oauth` are refused. As a basic user, `GET` is refused too. No response contains a token.
  - The admin change history has `vmcp.preconfigured_oauth.authorize` and `.revoke` for X, and `vmcp.preconfigured_oauth.invalidate` with actor `system` if the provider refused a refresh.
