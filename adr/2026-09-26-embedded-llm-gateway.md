# 2026-09-26: Embed an LLM gateway engine in Obot

- **Status:** Accepted
- **Date:** 2026-09-26
- **Supersedes:** None
- **Superseded by:** None

## Related ODPs

There is no ODP for this decision.

## Context

Obot's LLM gateway was a set of per-provider reverse proxies under `/api/llm-proxy/<provider>`, each with its own credential handling, URL construction and response parsing. Every new provider needed new proxy code, and every route served only one API dialect. The gateway had none of the features that dedicated gateways offer: load balancing across keys, retries and fallbacks, spend budgets, rate limits, routing rules, caching, and request analytics.

The chosen gateway engine is an Apache-2.0 Go gateway ([engine source](https://github.com/maximhq/bifrost)) that provides these features across 20+ providers and translates between the OpenAI Chat Completions, OpenAI Responses and Anthropic Messages APIs. It can run as a standalone service or be imported as Go modules.

## Decision

Obot imports the engine's HTTP transport (`github.com/maximhq/bifrost/transports`) and runs it inside the Obot process (`pkg/llmengine`).

- **No network listener.** The engine's fasthttp server is served over an in-memory listener. Obot reaches it through an `http.RoundTripper` that dials that listener, so nothing outside Obot can talk to the engine directly. The engine's own auth and virtual-key enforcement are therefore off.
- **Obot stays the policy layer.** `/api/llm-proxy/v1/{path}` (the root of the LLM proxy; `/api/llm-proxy/openai` and `/api/llm-proxy/anthropic` are aliases) reuses the existing LLM proxy pipeline (`llmProviderProxy`) with a gateway-engine backend. Obot still authenticates the caller and checks model access policies for the requested model. Inside the gateway, the same check runs again for each model it actually tries, so routing rule targets and fallbacks are covered too. It also enforces budgets, and records its LLM audit log and token usage. Guardrails run inside the gateway as Obot plugins (see [the guardrails ADR](2026-09-26-guardrails.md)). The engine then does routing, key selection, retries, fallbacks and translation.
- **One built-in model provider.** The `llm-gateway-model-provider` ModelProvider represents the gateway, with no daemon and no credential (like the local auth provider). Its models are listed from the engine as `provider/model` and synced into `Model` resources, with the engine's pricing projected into `ModelInfo`. Existing features that key on Models work without special cases, including access policies, default aliases and the MCP tester.
- **Profiles decide who gets what.** A profile is a model access policy extended with budgets and guardrail policies, after the profiles vMCPs introduced: it names users and groups (including Obot groups), the models they may use, and the budgets and guardrail policies that apply to them. Profiles add up. Budgets and guardrail policies match callers only through their profile, using the same indexed matching as model access, so there is one notion of who a subject is. Deleting a profile deletes its budgets and guardrail policies. Routing rules, fallbacks, providers and guardrails stay global.
- **Obot enforces budgets.** Budgets (`llm_gateway_budgets`) cap spend, tokens or requests over rolling or calendar windows. Each budget is either per user or one shared pool, belongs to a profile, and covers only that profile's models: all of them, or the ones it names, which the profile must grant. A budget applies to a request only when the caller is in its profile and the profile grants the model, so a profile's budgets don't limit models the caller gets from other profiles, and when several profiles' budgets cover a model, the tightest one limits it. Guardrail policies, by contrast, apply through every profile the caller is in. Obot checks every budget that applies to the caller and to each model the gateway tries (routing rules and fallbacks can serve a request with another model) against usage recorded in `llm_gateway_budget_usage`, and records the request's usage, priced at the serving model's rates, against that model's budgets. Access to each tried model is checked the same way. This replaces the daily token quota for gateway traffic; the configured quota is carried over once, as a copy of a per-user *Daily token limit* budget on every profile that exists at the upgrade, so it still covers every model a user can reach (a user in several profiles gets an allowance from each). A migration marker records that it ran, so copies an administrator edits or deletes stay that way and later profiles get none.
- **The engine prices requests; Obot records them.** Obot's output plugin asks the engine's model catalog what each response cost, for the model that served it (long-context and cache rates included), and Obot records that as the request's spend in its audit log, token usage and budgets. An administrator's cost override on a model wins. Obot keeps the only records of requests: the engine's request log is off.
- **Model data comes from Obot, not the engine's vendor.** The engine downloads its pricing datasheet and model parameters from its vendor's website by default, and exits the process when it starts with an empty store and can't download them. Obot instead embeds a snapshot converted from LiteLLM's MIT-licensed model list (`pkg/modeldata`), downloaded when CI builds the published Docker images and release binaries rather than committed, writes it to the gateway's data dir, and points the engine at it with `file://` URLs. Obot refreshes those files every 6 hours from `--llm-gateway-model-data-url` (`https://upgrade-server.obot.ai/v1/model-data` by default, which serves the same conversion), keeping the current files when a download fails or looks incomplete. A build without the snapshot, such as one from source, downloads the files when it starts and starts without model prices if it can't. The engine re-reads them hourly. Its MCP library sync, also from its vendor, is off.
- **The engine keeps its own configuration.** Providers, keys, virtual keys, routing rules and plugin settings live in the engine's config store, with provider keys encrypted (see Consequences). It is a SQLite file in the Obot data directory when Obot uses SQLite. When Obot uses Postgres, it lives in a `<database>_llm_gateway` database on the same server, which Obot creates if needed; `--llm-gateway-postgres-dsn` overrides this. If the database can't be created, the gateway doesn't start and says how to create it. It never falls back to SQLite on Postgres, because with several replicas each would keep its own providers, keys and routing. The engine's table names collide with Obot's, so the store cannot share Obot's schema.
- **Obot UI for everything.** The gateway's admin pages, under `/models` and `/usage`, use a guarded pass-through, `/api/llm-gateway/admin/*` to the engine's `/api/*`. It exposes only providers and their keys, models, routing rules, pricing overrides, the engine's client and proxy configuration, and its version. The engine's MCP, skills, prompt-repository, plugin, cache, log and feature flag APIs are not exposed, and the engine's own UI is not served. Its dashboard agent (Warp), on by default, is turned off in the configuration Obot generates. Response caching isn't offered.
- **The engine is not part of Obot's external interface.** No path, provider or model ID names it. The gateway strips the engine's response headers (which name upstream keys) and its `extra_fields`/`is_bifrost_error` body fields, from JSON and streaming responses alike. Client tuning headers use Obot names (`X-Obot-Session-ID`), and metrics are republished as `obot_llm_gateway_*`. That keeps the engine replaceable.
- **The gateway replaces model providers.** The legacy per-provider routes, their backends and model provider daemons are removed, and the gateway can't be disabled. On first start, the credentials of configured legacy model providers are imported into the engine. After each gateway model sync, default model aliases and model access policies that named a legacy model move to the gateway model for the same upstream model, and legacy models and providers are then deleted. The former per-provider routes other than OpenAI and Anthropic answer 410.

## Rationale

- **Budgets in Obot, not the engine's virtual keys.** The engine's open-source edition keeps governance counters in memory per process and writes them to the database every 10 seconds with last-writer-wins, never folding in other replicas. Cross-replica synchronization is an Enterprise feature. With several Obot replicas a budget could be overspent up to about N times, and the engine's stored usage would undercount. Its per-user limits are also Enterprise-only; open-source limits attach to virtual keys, teams and customers. Obot already records exact per-request usage in its shared database, so enforcing budgets there is accurate across replicas, keys on Obot identities, and supports per-user and shared pools.
- **Egress proxy.** The engine's HTTP client ignores `HTTPS_PROXY`, so Obot copies the environment's proxy onto each provider (honoring `NO_PROXY`) through the engine's per-provider proxy setting.

- **Pricing data.** The engine's own datasheet is built from LiteLLM's list, adds snapshot and regional entries, and is served under terms that forbid redistributing it. Converting LiteLLM's list directly gives the same prices for current models (checked by pricing every chat model with the engine's calculator against both). It needs no call to a competitor's site, works air-gapped from the bundled copy, and can be corrected centrally on Obot's upgrade server. The engine falls back to built-in, name-based defaults for capability flags LiteLLM doesn't have.

- **Embedding versus a sidecar.** Embedding avoids deploying, securing and versioning a second service. Running the engine's full transport rather than only its `core` library brings its governance, logging and routing plugins and its management API, all of which would otherwise need reimplementing.
- **Obot as the policy front, not an engine plugin.** Obot's authentication, access policies, message policies and audit log already exist and are tied to Obot's data model. Keeping them in front of the engine preserves them unchanged and keeps one enforcement point for every Obot principal type (users, API keys, hosted agents).
- **One synthetic provider.** Registering one provider with provider-qualified model IDs, instead of one ModelProvider per engine provider, keeps the engine the source of truth for provider configuration. It avoids a two-way sync.

## Consequences

- Obot's `go.mod` now carries the engine's dependency tree. The engine's `transports` module is consumed by pseudo-version because its v2 tags don't use a `/v2` module path. Upgrading the engine is a dependency bump, but its internal APIs (`BifrostHTTPServer`, `lib.Config`) are not a stable contract.
- Each Obot replica runs its own engine, and the replicas share configuration through the Postgres store. The engine's open-source edition loads its configuration into memory at startup and only updates that copy for changes made through it. So, following the pattern used for auth and model provider daemons ([2026-09-01 ADR](2026-09-01-provider-daemon-sync.md)), every gateway configuration change advances an `llm-gateway` revision in the `ProviderSync` singleton. A controller on every replica then rebuilds that replica's gateway from the store. New requests go to the rebuilt gateway; requests already in flight finish on the old one, which stops after up to 15 minutes. The replica that made the change does not reload unless it had missed an earlier one, or the change was to the engine's client configuration, parts of which only take effect when the engine starts.
- Gateway changes that Obot makes on its own, and admin writes through the management API, are serialized across replicas. Startup does three of these: it imports legacy credentials, configures providers from environment keys and applies the egress proxy. Before changing anything, a replica takes a Postgres advisory lock that every replica shares and reloads to the latest revision. Without that, two replicas starting together each change their own in-memory copy and write it back, and the later write erases the earlier one (for example, an imported key). The lock is a session-level advisory lock (`pg_try_advisory_lock`) on a connection of its own, held until the change returns, so it can't expire while a change is still being made (a timeout that rolled back a transaction-scoped lock mid-change would let another replica write a stale copy). A crashed replica's connection closes and Postgres releases the lock. Taking it waits at most 5 minutes; lock waits are short in practice because the critical sections are startup and admin edits. The cost is one pooled connection held for the critical section, which can include a full gateway reload; no transaction stays open meanwhile. SQLite deployments are single-replica and use no lock.
- The engine's own virtual-key budgets are not used, because they don't aggregate across replicas. With SQLite, which is single-replica only, each replica would have separate state.
- The engine encrypts provider keys and other secrets in its store with AES-256-GCM, using the gateway's encryption key. That key is `--llm-gateway-encryption-key` when set. Otherwise Obot generates it and, for Postgres deployments, stores it as a credential in Obot's database, so every replica uses the same one and it is encrypted with Obot's own encryption configuration (for example KMS) when one is configured. For SQLite deployments it is stored in the data dir. Without an Obot encryption configuration, the key and the encrypted provider keys are on the same Postgres server, so configure one, or set the key from a secret store, for real protection at rest.
- Routing rules and fallbacks can only reach models the caller may use. The access and budget check runs on every attempt the gateway makes, so a routing target the caller isn't granted is refused with 403. Administrators who route requests to another model must grant that model too.
- Only endpoints Obot can meter and guard are exposed: Chat Completions, Responses, Messages and embeddings, plus model listing and token counting (`messages/count_tokens`, `responses/input_tokens`). Embedding models can't yet be granted through a profile, so embeddings aren't reachable until they can. Images, audio, rerank and batch APIs need metering before they can be exposed.
- Clients set up for the removed Bedrock, Azure and generic Responses routes must move to `/api/llm-proxy/v1`.
