## Context

Automation in Obot ran as users, with user-owned API keys. An agent's access, upstream credentials and audit trail were therefore tied to whoever created its key. Policies changed when that person changed roles or left, and vMCP connections that needed configuration or upstream OAuth prompted an interactive user who was never there.

Several things in the codebase already used the word "agent": hosted agent sessions (`v1.AgentInstance`), AI agents on managed devices (`pkg/localagents`, `LocalAgentToolCall*` audit fields), and the Identity & Access "Agents" tab, which listed a user's own API keys. Every owner field in storage held a decimal user ID, and about 125 call sites parsed it as one.

## Decision

### Identity and storage

- **Typed principals with a hybrid owner encoding.** `pkg/principal` gives every caller and owner a kind (`user` or `agent`) and an ID. Owner strings in storage (`spec.userID` on stored objects and `UserID` keys in gateway tables) hold `"<uint>"` for users, unchanged, and `"agent:<id>"` for agents. All reads and writes go through `principal.Parse` and `Principal.String()`. API responses and audit tables expose a typed `{kind, id}` (`types.PrincipalRef`). Authenticators record the kind in `Extra["obot_principal_kind"]` with `principal.RecordKind`, which always overwrites what a provider supplies. `principal.FromUserInfo` requires the marker and rejects a marker that disagrees with the UID.
- **Call-site classification.** Each `GetUID()`, `ParseUint(userID)` and `api.Context.UserID()` site was classified as: (1) needs a user, which rejects agents explicitly, with `api.Context.UserID()` still 0 for non-users; (2) any owner, which stores and compares `Principal.String()`; or (3) policy matching, which moved to `pkg/subjects`. Stored owners are reloaded through `gateway/client.IdentityInfo`. `pkg/principal/guard_test.go` fails on new user-ID parses of owner strings outside the allowlist.
- **Agents are gateway identities.** `gatewaytypes.Agent` (table `agents`) has a display name, a description, an immutable `CreatorUserID`, and active, disabled or deleted states. Rows are only soft-deleted, so agent IDs are never reused and deleted agents still resolve for audit display. Lifecycle changes write an `AgentLifecycleEvent` in the same transaction. The user outbox delivery loop is now generic and delivers both event types as idempotent `v1.AgentIdentityChange` (prefix `aic1`) and `v1.AgentIdentityDelete` (prefix `aid1`) objects. Cluster and API types use the `AgentIdentity` name to avoid clashing with `AgentInstance`.

### Keys and authentication

- **One key table, two owner kinds.** `api_keys.user_id` became a nullable `*uint` in Go (the column was already nullable), with a new nullable `agent_id` and a `CHECK ((user_id IS NULL) <> (agent_id IS NULL))`. The migration runs once through `migrateIfEntryNotFoundInMigrationsTable`. Agent keys use the prefix `oak1-<agentID>-<keyID>-<secret>`. User keys keep `ok1-`. Parsing is driven by the prefix, and the agent validation path filters on `agent_id`, so `oak1-5-7-…` never matches user 5's key 7. The 15-second validation cache still re-reads revocation, expiry and the owner's status on every hit.
- **Key scopes match user key scopes (decision 6).** An omitted scope isn't granted, at least one of MCP, LLM and Skills is required, and an empty `mcpServerIds` means no MCP. Agent keys never carry `CanAccessAPI` or `CanAccessDeviceScans`. Effective access is computed live as the intersection of the key's scopes and the agent's current grants, so grant changes apply to existing keys.
- **Agent route allowlist.** An agent principal is authorized only by `pkg/api/authz/agent.go` and never by the user rules. It reaches `/api/llm-proxy/` with the LLM scope, `GET /api/skills…` with the Skills scope, MCP connections with an MCP scope (and internal composite connections), and the API key webhook. System MCP servers are excluded. A principal that claims to be an agent but carries any other group, such as `api` or a role group, reaches nothing. Any new route that agents need must be added there.
- **Loopback tokens and webhooks.** Internal loopback JWTs carry the encoded owner and a `PrincipalKind` claim. Old tokens without the claim are users. The agent branch checks the agent's current status on every request and refuses to mint for a non-active agent. The API key webhook returns `sub: "agent:<id>"`. MCP OAuth token minting rejects agents.
- **No feature flag (decision 8).** Agent identities are always on. The hidden `EnableAgentIdentities` option existed during development and was removed before release.
- **Agents work with authentication off (decision 9).** With authentication disabled, the single owner manages agents, and an `oak1-` key or agent loopback token authenticates as its agent, with the agent's allowlist and scopes, ahead of the catch-all owner. A presented agent credential either authenticates or is refused. It never falls through to the owner.

### Policy subjects

- **Agents are named only by ID (decision 5, as changed).** An explicit agent is `{agent,"<id>"}` with the bare decimal ID, and it is the only subject an agent matches. There is no agent wildcard: `{agent,"*"}` (`agents:*`) is refused by subject validation in every system, by guardrail filter validation, and by catalog validation, with an error that says agents must be named by ID. The one wildcard is the existing `{selector,"*"}` (`subjects:*`), labeled **All Obot Users** as before: it matches every user and no agent, in every policy system. `{user,"*"}` keeps its existing meaning, an ordinary user subject that matches nobody, and is validated as it always was. `pkg/subjects.Evaluate` is the shared matcher for the grant systems, and `pkg/subjects.EvaluateRestriction` for guardrail filters. Agents never match user, group or Obot group subjects. Policy indexes key subjects by kind (`user:<id>`, `agent:<id>`, and `*`), and an agent looks up only `agent:<id>`, so a user and an agent with the same numeric ID never find each other's policies.
- **Where agents can be named.** Agent subjects are accepted by vMCP profiles, model access policies, skill access rules and MCP guardrail filters. MCP guardrail filters use their own subject type, where the wildcard is `everyone`. It restricts every user and no agent: a filter restricts an agent only if it names the agent by ID. A caller that is neither an identified user nor an identified agent still matches `everyone`, so a filter for everyone can't be escaped by a caller Obot can't identify. Access control rules and message policies reject agent subjects, and access control rules never match an agent. No stored subject is migrated: agent identities were unreleased when agent wildcards were removed, and a `{agent,"*"}` stored during development matches nobody and fails validation on its next save.
- **CEL.** Guardrail conditions (LLM and MCP) keep `user.id` as the storage encoding (`agent:<id>` for agents) and `user.groups` (empty for agents), and add `principal.kind` and `principal.id`.

### vMCP profiles, agent setup and OAuth grants

- **Profiles are subjects and permissions only.** A profile holds no data for agents, as it holds none for users: no configuration, no OAuth grant and no setup status. Everything agents need from a vMCP beyond access is on the vMCP itself.
- **Profile IDs.** Profiles have immutable IDs, which the admin change audit and MCP audit records name them by. API-managed vMCPs get server-assigned `vp1<random>` IDs, carried by ID on update. A profile without an ID is new, even with an existing name, and invented IDs are rejected. Catalog YAML may set `id`. Otherwise the ID is `vp1` plus a hash of the vMCP and profile names, so renaming a profile in YAML without an `id` creates a new profile. The vMCP controller gives profiles stored before IDs existed their derived ID.
- **Agents in profiles, like users (catalog vMCP handling, decision 3).** An agent may be named by several profiles of a vMCP, on API-managed and catalog-synced vMCPs alike, and gets the union of their components and tools, exactly as a user does (`vmcp.MatchingProfiles`, `vmcp.AllowedTools`, `vmcp.EnabledComponents`). Removing the agent from one profile takes away only that profile's grants. An agent that no profile names isn't granted the vMCP: it can't connect, and readiness doesn't list it. There is no rule about wildcard profiles across a vMCP, as before agent identities. Catalog YAML may name explicit agents. Their IDs belong to one deployment, so `obot mcp validate-catalog` checks only their form, and on sync an ID that names no agent, or a deleted one, matches nobody, as a deleted agent's subjects do, without failing the sync. A profile is agent-capable (`VMCPProfile.IsAgentCapable`) when it names an agent by ID, and the components agent-capable profiles grant are the ones the vMCP's agent setup covers.
- **Agents use only configuration fixed for everyone.** An agent never enters configuration, and nothing enters it for an agent. Its component servers get only the values the vMCP fixes (the `fixed` policy, with a value or a Secret) and the values its catalog entry supplies (static values and Secret bindings). A `userAllowed` value is never given to an agent: an optional one is left unset, and a required one, including a hostname-constrained remote's `__url` that the vMCP does not fix, blocks every agent granted the component from the whole vMCP (`vmcp.AgentMissingConfiguration`). Connect returns 409 `agent_configuration_required` and readiness reports `configuration_required`, naming the component and key. The fix is to set the value as fixed on the vMCP or in the catalog entry, or to stop granting the component to the agent. An agent instance's configuration credential (`vmcp-instance/<id>`) is never read (`vmcp.InstanceTakesUserConfiguration`), and admins can't configure, deconfigure or reveal agent-owned instances through `/api/vmcp-instances` (409), so no one can give an agent a value a user would enter. The existing per-component sharing decision (`vmcp.IsMultiUser`) holds for agents unchanged.
- **Agent OAuth grants are per vMCP component.** A vMCP holds at most one agent OAuth grant per component, which every agent that a profile of the vMCP grants the component uses, and no other agent. An administrator authorizes it once, in the vMCP's agent setup (`POST /api/vmcps/{vmcp_id}/agent-oauth/{component_id}`), and revokes it there (`DELETE` on the same path). Only remote components that an agent-capable profile grants can be authorized. A grant is a `gatewaytypes.MCPOAuthToken` row with owner `vmcp-agent-oauth:<vmcpID>` (which `principal.Parse` never accepts, so it can never authenticate) and `MCPID = <vmcpID>/<componentID>`. Catalog static OAuth clients remain authoritative for client identity. Pending state binds the initiating admin, the vMCP, the component, the target URL and the component definition hash. The callback requires the same admin and checks all of them again. A grant is bound to the URL agents reach: the URL the catalog fixes, or the `__url` or URL template built from the values the vMCP and the catalog entry fix. It is checked again at readiness and at every component hop. A mismatch is `oauth_invalid`. Localhost-callback components hold grants too: only the one-time authorization goes through the `obot mcp login` relay, within 10 minutes, as the initiating admin. A broken grant is `oauth_invalid` until an administrator authorizes it again. Starting an authorization finds the challenge with unauthenticated probes that carry no configured header or token and end their session: `initialize`, then `tools/list` in the same session, then the server's RFC 9728 protected resource metadata, so servers that challenge late can be authorized. Readiness never probes. A component counts as requiring OAuth when it requires static OAuth, the vMCP holds a grant for it, valid or not, or the vMCP controller's background probe found that it asks for OAuth.
- **Grant cleanup.** Every grant is recorded in `status.agentOAuthGrants` (component and grant IDs) at a resource version whose spec still has the component, before it is stored, and published there once stored. The vMCP controller deletes a component's grant when the component leaves the manifest, and the vMCP's finalizer deletes all its grants. Profile changes and agent deletion delete no grant: a grant for a component that no profile grants to an agent any more stays, unused and unlisted, and applies again if a profile grants the component to an agent. Nothing is keyed by profile ID, so there is no per-profile cleanup and no guard against replacing a profile.
- **Background OAuth probe.** The vMCP controller (`ProbeComponentOAuth`) runs the same unauthenticated probe, through `SessionManager.ProbeOAuthRequirement`, for each remote component that an agent-capable profile grants, at the URL agents reach, and skips one whose URL needs a value nothing fixes. It records `True`, `False` or `Unknown` in `status.componentOAuth[componentID]`, with a target hash (`vmcp.ComponentOAuthTargetHash`: the component definition, the catalog entry's static configuration revision and the digest of the values the vMCP fixes for the component), never the URL. It probes again when the target hash changes and every 24 hours, and retries failures after 1 minute, doubling to at most an hour. A failure keeps the last successful result for the same target, or records `Unknown`, which counts as not required, so a flaky server never blocks agents. A 401 counts only when Obot's own OAuth discovery would start an authorization from it. Components that take configured headers, and static-OAuth components, aren't probed: a server that challenges a request without an API key header may accept one with it. Readiness, agent setup and connect read only the recorded result.
- **Refresh lock.** Shared grants are refreshed under a per-token in-process lock. On Postgres, a transaction-scoped advisory lock keyed on owner and MCPID follows. At most two refreshes per process hold a database connection at once (`mcpOAuthRefreshHolders`). A waiter re-reads the row and uses the token the holder saved. `invalid_grant` marks the grant invalid for every agent, and transient failures don't.
- **Readiness is computed on the vMCP, and shared with the connect path.** A vMCP is ready for an agent when every component that the agent's profiles grant (the union) is ready: it needs no value agents can't be given, and, if it requires OAuth, the vMCP holds a working grant for it. Components no profile of the agent grants don't count. The connect path and the readiness API both call `SessionManager.AgentReadiness`, and nothing is cached. Any reason blocks the whole connection. Agents get 409 with `agent_configuration_required` or `agent_oauth_required` and `reasons` that name the component, and every reason is fixed on the vMCP. They never get `WWW-Authenticate`, a redirect or an MCP OAuth challenge row, including through composite loopbacks. A refused agent key gets a plain 401. Transient deployment and upstream failures keep their 502/503 paths. The vMCP's agent setup (`GET /api/vmcps/{vmcp_id}/agent-setup`) reports the same checks per component, for every component an agent-capable profile grants; it is the only status of agent setup.

### Lifecycle, audit and redaction

- **No owners, only a creator (decision 7).** The ODP's owner list granted nothing and was removed. `CreatorUserID` is set automatically and is immutable. It is 0 for a caller with no user row, such as the bootstrap admin.
- **Cleanup mirrors user cleanup (decision 7a).** Disable removes nothing. Authentication refuses the agent on its next request, including on cache hits and with loopback tokens. Delete revokes keys in the delete transaction. The cleanup controller then removes the agent's vMCP instances, standalone servers and connections, with their credentials and tokens. Subjects stay in policies and match nobody, as a deleted user's do. vMCP agent OAuth grants are untouched, and audit and usage rows are kept.
- **Activity attribution.** LLM audit, MCP audit, token usage and budget usage rows gain `principal_kind` (default `user`) and `principal_id`. Agent rows leave `user_id` empty, except budget usage, which keys counters on `agent:<id>`. There is no backfill: a row without `principal_id` reads as the user in `user_id`. MCP audit rows also record the vMCP, the component, and the contributing profile IDs, which for an agent are every profile that names it. Agents record no daily API activity.
- **Budgets.** Budgets apply per principal, so an agent and the user with the same numeric ID count separately. `ExemptAdmins` never exempts an agent. Users' personal daily token limits, including the migrated *Daily token limit* budget's per-user override, don't apply to agents, which get the budget's own limits.
- **Secret-free admin change audit (decision 4).** `gatewaytypes.AdminAuditEvent` records agent, key, policy-subject, profile-subject and agent OAuth grant changes made through the admin API, with the acting admin, plus `system` events for grant invalidation and grant removal. Grant events are recorded against the vMCP (`resourceKind` `vmcp`), with the component in their details. Details name fields, subjects, scopes and hostnames, never configuration values, tokens, key secrets, configured URLs or disable-reason text. Retention reuses the API-key rule: the longer of the MCP and LLM audit retentions, or forever if either is 0. `admin` is a new audit log export type.
- **Redaction of configured URLs.** A URL that comes from the vMCP's fixed configuration is treated as a value. Agent setup and readiness report only its hostname (`targetHostname`). Authorize errors replace it with placeholders. The admin audit, Read-Only Admins, auditors and the UI never see it. A full `target` URL is shown only when the catalog fixes it.

## Rationale

- The hybrid encoding left every user row, owner string and user API response byte-for-byte unchanged, yet made a user and an agent with the same numeric ID distinct everywhere owners are stored or compared. A separate owner-kind column on every table, or reusing users with a flag, would have touched far more storage or blurred the two identity models.
- A Gateway table plus the existing outbox kept key and identity lifecycle in one transactional store, which the ODP preferred to a v1 resource.
- A single `api_keys` table with a CHECK constraint reused hashing, one-time disclosure, expiry, revocation and last-used tracking, and the database enforces exactly one owner.
- An allowlist for agents fails closed: a route added for users is not reachable by agents until someone decides it should be.
- Agents are named only by ID, and wildcards and guardrail `everyone` cover users only, because granting or restricting an agent should always be deliberate. A policy written for people, including every policy written before agents existed, never reaches an agent, and an agent's access can be read from the policies that name it. `{user,"*"}` keeps the meaning it always had, so no stored subject changes meaning.
- Matching user key scopes (decision 6) gave one scope model in the API, CLI and UI, and an agent key does nothing its creator didn't ask for. Removing owners (decision 7) dropped metadata that granted nothing but still needed cleanup. Mirroring user cleanup (decision 7a) kept one, already-proven model for what deletion does to policies.
- Profiles stay subjects and permissions only, for agents as for users, so an agent's permissions on a vMCP are read the way a user's are: the union of the profiles that name it. Agent OAuth grants and setup moved from profiles to the vMCP, one grant per component, so an administrator authorizes a component once rather than once per profile, and no per-profile data needs cleanup, replace guards or a rule that keeps each agent in one profile. Grants were first built per profile, with each agent limited to a single profile of a vMCP, and then moved to the vMCP. A grant is bound to the component's fixed URL, which is the same for every agent of the vMCP, so one grant per component serves them all. The cost is that agents of one vMCP can't use different upstream accounts for the same component.
- Agents use only configuration fixed for everyone. Profile-level configuration for agents was built first and then removed: per-profile secrets for agents weren't worth their storage, revisioning, garbage collection and launch-path complexity (an instance sync controller and a connect wait). A component that needs user input is rare for unattended automation, and an administrator can fix the value on the vMCP or the catalog entry, which also keeps runtime sharing decisions unchanged. A component that needs user input blocks the vMCP for agents rather than serving fewer tools.
- Hostname-only URL reporting and the secret-free audit stop any API, log or audit row from becoming a side channel for configured secrets.
- Sharing readiness with the connect path means the readiness API can't promise a connection that would then fail.

## Consequences

- New code that reads an owner must go through `pkg/principal`, and new in-process principals used for policy matching must call `principal.RecordKind`. A principal without a kind matches no subject.
- New routes are closed to agents until they are added to `pkg/api/authz/agent.go`.
- Agents can be named in four policy systems and must never be named in access control rules or message policies. A policy system that adds subject matching must decide which side it is on, and must match agents only by ID.
- Granting an agent anything means naming it in each policy. There are no agent groups and no agent wildcard.
- Profile renames are safe in the API. In catalog YAML, a profile without an explicit `id` gets a new ID when renamed, which only audit records see.
- Data kept for agents on a vMCP outside its manifest must be deleted with its component and with the vMCP, as agent OAuth grants are (`status.agentOAuthGrants` and the vMCP finalizer).
- All agents granted a component share the vMCP's one grant for it, and so its upstream account and scopes.
- A vMCP component that needs a `userAllowed` value can't be used by agents until the value is fixed for everyone or the component is no longer granted to them.
- Rolling back requires disabling agents and removing agent subjects and vMCP agent OAuth grants before downgrading (see [Rollout and rollback](#rollout-and-rollback)). The schema additions stay.
- Mid-stream MCP errors can't yet carry the reason code. That needs a hook in the MCP proxy library.

## Rollout and rollback

There is no flag. Each part is live once it merges, so the stack merges in order. A spec doesn't merge ahead of the specs that make its routes complete. Users' behavior doesn't change. Replicas of mixed versions are safe: older replicas ignore the `obot_principal_kind` claim and the `PrincipalKind` loopback claim, and refuse `agent:` subjects in loopback tokens.

Rollback:

1. Disable every agent (`obot agents disable <id>`), so no agent credential authenticates.
2. Remove `{agent,…}` subjects from model access policies, skill access rules, vMCP profiles and MCP guardrail filters. Older versions refuse to save a policy that names an agent.
3. While still on this version, revoke every vMCP's agent OAuth grants (`DELETE /api/vmcps/{vmcp_id}/agent-oauth/{component_id}`). Older versions ignore grant token rows (owner `vmcp-agent-oauth:…`), which would otherwise stay at rest, and any vMCP write by an older version drops the status field that tracks them, so a later upgrade can't find them. If revoking isn't possible, delete OAuth token rows whose `user_id` starts with `vmcp-agent-oauth:`.
4. Delete the agents, so their keys are revoked and their instances removed.
5. Downgrade the binary.

Schema additions stay in place, and nothing needs to be altered back: the `agents`, `agent_lifecycle_events` and `admin_audit_events` tables, `api_keys.agent_id` and the CHECK constraint, the audit and usage principal columns, the MCP audit vMCP, component and profile columns, and the token and pending-state grant columns. Older versions use gorm AutoMigrate, which never drops or tightens these, and their writes satisfy the CHECK. Revoked agent keys stay in `api_keys` with a NULL `user_id`. Older versions read it as user 0, list it in the admin key list, and can't authenticate it, because they parse only `ok1-` keys and match on `user_id`. A rollback rehearsal on Postgres 16 ran the pre-feature binary (`d2d8508c7`) on a database written by this version, with and without these steps, and then this version again. All three started, migrated and served user keys, admin key lists and audit logs.

## Departures from the ODP

Each of these differs materially from the accepted ODP.

1. **Key scope defaults (decision 6).** The ODP defaults omitted agent-key restrictions to `MCPServerIDs: ["*"]`, `CanAccessLLMProxy: true` and `CanAccessSkills: true`. Shipped: agent key scopes work as user key scopes do. An omitted scope isn't granted, at least one scope is required, and an empty MCP list means no MCP access.
2. **No owners (decision 7).** The ODP gives agents ownership metadata. Shipped: no owners. Only an immutable `CreatorUserID` is recorded.
3. **Deletion leaves subjects in place (decision 7a).** The ODP says deletion removes explicit agent subjects from vMCP profiles, model access policies and skill access rules. Shipped: subjects stay and match nobody, as a deleted user's do. Agent IDs are never reused, so a stale subject can't grant a later agent anything.
4. **Profiles carry no agent data.** The ODP lets profiles supply configuration for agents, including "optional overrides of vMCP-fixed values", and holds agents' OAuth grants on profiles, with per-profile setup status. Shipped: profiles are subjects and permissions only. Agents get only values fixed by the vMCP or the catalog entry, and a granted component that needs a `userAllowed` value blocks the vMCP for agents. Agent OAuth grants are per vMCP component, shared by every agent granted the component, and readiness and setup status are computed on the vMCP over the components the agent's profiles grant.
5. **Agents work with authentication off (decision 9).** The ODP doesn't cover this mode. Shipped: the single owner manages agents, and agent keys authenticate as their agents ahead of the catch-all owner.
6. **No feature flag (decision 8).** The ODP's rollout adds the schema and enforcement "before enabling agent creation and policy editing". Shipped: there's no switch, and merge order is the only gate.
7. **MCP guardrail filters accept explicit agent subjects.** The ODP limits agent subjects to vMCP profiles, model access policies and skill access rules, and says "do not expand wildcard semantics in unrelated policy systems". Shipped: MCP guardrail filters can name agents by ID. Their `everyone`, and a filter with no subjects, never apply to an agent, so a filter restricts an agent only when it names it.
8. **Agents are named only by ID.** The ODP defines `subjects:*` as every user and every agent, adds `users:*` and `agents:*`, and resolves an agent's OAuth grants from its explicit profile, falling back to a wildcard profile, with rules that keep the wildcard profiles of a vMCP unambiguous. Shipped: there is no `agents:*`, `{user,"*"}` matches nobody as before, and `subjects:*` matches users only, so an agent matches only a subject that names it. An agent named by several profiles of a vMCP gets their union, as a user does, and uses the vMCP's grant for each component it is granted, with no fallback and no ambiguity. Catalog YAML may name agents by ID, unchecked by `obot mcp validate-catalog` beyond their form (decision 3, as changed). Granting or restricting an agent is always deliberate.
9. **Mid-stream errors carry no reason code.** The ODP says an already-started response uses the protocol's error path. Shipped: no challenge is ever issued, but a JSON-RPC error inside an already-started stream can't yet carry `agent_oauth_required` or the component.
10. **Refused agent keys get a plain 401.** The ODP keeps the existing authentication failure behavior for an invalid credential. Shipped: a refused agent key gets a plain 401 without `WWW-Authenticate` on MCP connections. The registry (`/v0.1`) still challenges.
11. **Admin change audit coverage.** The ODP audits lifecycle, key, profile, model and skill policy, and OAuth changes with the acting admin. Shipped: only changes made through the admin API, plus `system` grant invalidation and removal. Catalog-synced vMCP subject changes and controller-side changes are not recorded.
12. **Skills activity attribution.** The ODP attributes Skills activity to the agent and key. Shipped: skill downloads remain unaudited, for users and agents alike. That gap already existed.
13. **Grant revocation doesn't revoke at the provider.** The ODP's "revocation" covers grants. Shipped: revoking deletes the grant locally without RFC 7009 revocation, as users' resets do.
14. **Additions beyond the ODP.** These are recorded so the follow-up ODP can accept them explicitly: CEL `principal.kind` and `principal.id`; the API key admin list filters by `?kind=user|agent`; localhost-callback grants through `obot mcp login`; the `admin` audit export type; and the rename of the user API key tab from "Agents" to "API Keys".
